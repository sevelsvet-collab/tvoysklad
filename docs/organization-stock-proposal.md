# Складской учёт по организациям — воспроизведение и план перехода

Статус: **реализовано 18.10.2026** (раздел «Реализовано» ниже); разделы 1–11 —
исходное воспроизведение и план (колонка «Программа сейчас» — поведение до
реализации). Рабочая база, сервер и `.env` не трогались, ничего не закоммичено.

## Реализовано (18.10.2026)

**Ключ учёта — «организация + склад + товар».**

- `StockMovement.organization` — организация документа-источника (у новых
  движений всегда; пусто — только у старых без источника, это решает человек).
  `StockBalance` — уникальность (организация, товар, склад). Расчёт
  себестоимости (`costing.build_plan`), покрытия дефицита, проверки наличия
  (`services.validate_stock`, `check_history`), остатки на дату
  (`costing.state_on`) — по ключу. Поступление одной организации никогда не
  покрывает расход другой; возврат без основания оценивается только по истории
  своей организации и зафиксированной цене строки; перемещение — в ключах своей
  организации, чужой товар перемещать нельзя (`transfer_deficit`).
- Запрет минуса — по флагу **организации ключа**. При смене организации
  проведённого документа проверяются обе истории (прежней — по её флагу, новой —
  по её); отказ откатывает документ, движения, номера, покрытия, себестоимость
  и остатки (одна транзакция; проверено тестами). Смена организации,
  несовместимая с возвратами по документу, отклоняется (`return_limits`).
  Менять организацию проведённого документа можно только через механизм
  перепроведения — см. «Смена организации проведённого документа» ниже.
- Серийные номера: `SerialNumber.organization`, `SerialMovement.organization`,
  время и момент создания документа в движении номера (порядок истории как у
  складских движений). Принять номер, который где-то лежит, нельзя никакой
  организации; расходовать и перемещать — только той, у которой он лежит;
  история номера проверяется по владельцу. Номер без определённого владельца
  (ввод остатка без документа) расходовать нельзя, пока человек не решит.
  Ввод номеров остатка — с выбором организации.
- **Явный статус перехода** `StockLedgerState`: «ожидает пересчёта» →
  «выполняется или прерван» → «готово». Пока не «готово», складские операции
  (проведение, отмена, удаление документов, ввод номеров) отклоняются,
  страница остатков и карточка товара показывают предупреждение вместо
  остатков, отчёт «Продажи и прибыль» — предупреждение, подбор товара — без
  остатка. Пустая база — «готово» сразу (пересчитывать нечего).
- **Нарушения, которые создало разделение** (`StockTransitionIssue`):
  организация с запретом минуса ушла в минус там, где по складу в целом его не
  было (расходовала чужой товар). Записываются при пересчёте и блокируют
  операции с товаром (`transition_negative`), пока документы не исправлены
  целиком (снятие, смена организации — решение человека) или организации не
  разрешили минус. Автоматически допустимыми не считаются.
- **Фильтр организации:** остатки (текущие и на дату), подбор товара в
  документе (берётся организация из шапки), отчёт «Продажи и прибыль». Строки
  остатков — по организациям; сводка по складу при нескольких организациях —
  «в наличии» и «дефицит» порознь, средняя только по имеющемуся товару,
  помечена «справочно» и для проведения не используется. Итог стоимости —
  сумма по организациям. Деньги и взаиморасчёты — без изменений.
- Блокировка — по товару целиком (`lock_products`), порядок прежний.

### Смена организации проведённого документа (19.10.2026)

**Закрытый дефект.** Обычное сохранение проведённой приёмки
(`receipt.organization = Б; receipt.save(update_fields=["organization"])`)
переводило к Б документ и взаиморасчёты, а движение и остаток оставались у А:
закупка числилась за Б, складской актив — за А. Регрессионный тест —
`apps/inventory/tests_org_document_change.py`; до исправления он падал с
`{'документ': 'Б', 'движения': ['А'], 'остаток': ['А'], 'взаиморасчёты': ['Б']}`.

**Контракт** (`apps/inventory/posting.py`, правило 9). Организация документа и
его движений (складских и серийных номеров) всегда совпадают.

- **Единственный путь** сменить организацию проведённого документа —
  `doc.change_organization(организация)` или блок
  `with doc.editing(): …; doc.save()`. Это одна транзакция:
  1. строка документа блокируется, статус берётся из базы, а не из объекта;
  2. товары строк, движений и новых строк формы блокируются — порядок прежний:
     документ, затем товары по возрастанию id;
  3. выполняется тело блока; записать другую организацию разрешено только
     этому объекту и только внутри блока;
  4. при выходе документ перепроводится один раз: проверяются обе истории,
     возвраты и основания, серийные номера, покрытия, себестоимость и остатки;
  5. любой отказ откатывает всё, и у объекта восстанавливаются сохранённые
     организация и статус.

  Рекурсии нет: `save()` механизм не вызывает, а `post()` записывает только
  статус. Промежуточное состояние (новая организация при старых движениях)
  существует только внутри незавершённой транзакции под блокировками.
- **Форма документа** сохраняет существующий документ через `editing()`.
  **Административная панель** — через `editing(drafts_only=True)`: проведённый
  документ в ней не меняется. Если документ провели, пока страница была
  открыта, сохранение откатывается целиком и показывается сообщение.
- **Отклоняются до записи** (`OrganizationChangeError`), если документ проведён
  или у него есть движения:
  - `save()`, `save(update_fields=[…organization…])` и
    `save(update_fields=[…organization_id…])` с организацией, отличной от
    сохранённой. Сверка идёт с базой под блокировкой, поэтому устаревший
    объект не может вернуть прежнюю организацию;
  - `QuerySet.update(organization=…)` и `update(organization_id=…)`, в том
    числе через связанный менеджер. Выражение вместо значения считается сменой
    у всех документов выборки;
  - `bulk_update(…, ["organization"])`: одна недопустимая строка отклоняет
    весь пакет;
  - `bulk_create(update_conflicts=True, update_fields=[…organization…])` —
    не поддерживается;
  - `post()` объекта, у которого организация изменена в памяти, но не
    сохранена.

  Документ «с движениями» — это и черновик, у которого статус переписан мимо
  отмены проведения.
- **Остаётся допустимым:** смена организации черновика любым способом;
  `save(update_fields=["comment"])` при несохранённой смене организации в
  памяти — база не меняется, номер в серии новой организации не
  регистрируется, а проведение такого объекта отклоняется.
- **Связанные документы** вслед за документом не переносятся. Основание с
  проведёнными возвратами и возврат с основанием другой организации
  отклоняются (`return_limits`). Возврат-черновик после смены основания
  остаётся у прежней организации, и провести его нельзя, пока организации не
  совпадут.
- **Старые расхождения** (прямая правка базы) показывают
  `manage.py stock_transition` (с готовой командой исправления) и
  `check_costs` (перечень). Чтение отчётов и диагностика ничего не
  переписывают. Исправление — решение человека, через тот же механизм:
  `stock_transition --fix-organization ВИД:ID=document --i-have-a-backup` —
  движения переходят к организации документа; `…=movements` — документу
  возвращается организация движений. Если история не позволяет, отказ, и
  ничего не меняется. Обычное перепроведение документа равносильно
  `document`.
- **Не закрывается этим этапом:** прямой SQL и
  `Model._base_manager.update()` (их видит диагностика). Склад, дата и время
  закрыты следующим этапом (раздел ниже); строки документа — нет. Сверка
  организации счёта-основания отгрузки и договора с организацией документа
  не выполнялась и до этапа.

### Склад, дата и время проведённого документа (19.10.2026)

**Закрытый дефект.** Три сценария на приёмке подтверждены независимо через
`save(update_fields=[…])`: регрессионные тесты
`apps/inventory/tests_posted_requisites.py` до исправления падали.

| Поле | Документ после сохранения | Движение |
|---|---|---|
| `warehouse` | склад W2 | склад W |
| `date` | 10.01.2026 | 02.01.2026 |
| `time` | 18:00 | 12:00 |

**Контракт** — тот же механизм, что для организации (`posting.py`,
правило 9), но для всех **учётных реквизитов** (`STOCK_FIELDS`): организации,
склада, даты и времени. У перемещения защищены оба склада, отправитель и
получатель.

- Менять учётные реквизиты проведённого документа можно только через
  `with doc.editing(): …; doc.save()` или через форму документа. Это одна
  транзакция:
  1. блокируется строка документа, затем товары;
  2. выполняется запись;
  3. документ перепроводится один раз — прежняя и новая история: запрет
     минуса, себестоимость, покрытия дефицита, серийные номера, хронология
     возвратов и оснований.

  При отказе откатывается всё, а у объекта восстанавливаются сохранённые
  реквизиты. Админка, как и прежде, правит только черновики.
- Отклоняются до записи, если документ проведён или у него есть движения
  (`PostedChangeError`; если среди изменённых есть организация —
  `OrganizationChangeError`):
  - `save()` и `save(update_fields=[…])` — с именем поля или столбца
    (`warehouse` / `warehouse_id`);
  - устаревший объект;
  - `QuerySet.update()`, `bulk_update()`, `bulk_create(update_conflicts)`.

  Сравниваются фактически записываемые значения (объект → id, строка даты
  → дата) со свежим состоянием базы под блокировкой. Выражение вместо
  значения (`F("date") + …`) считается изменением, поэтому обхода через
  выражения нет. Массовое изменение защищённых реквизитов проведённых
  документов отклоняется целиком.
- `save(update_fields=["comment"])` склад или дату, изменённые только в
  памяти, не записывает. Проведение такого объекта отклоняется: «склад
  изменён, но не сохранён (в базе — «W», в документе — «W2»)».
- **Диагностика.** До этапа ни `check_costs`, ни `check_returns`, ни
  `stock_transition` таких расхождений не видели: на временной базе с 4
  расхождениями все три ответили «Расхождений нет», «Нарушений нет», 0
  проблем. Теперь `transition.requisite_mismatches()` сверяет склад, дату и
  время каждого документа с его складскими движениями и движениями номеров:
  - у перемещения расход сверяется со складом-отправителем, приход — со
    складом-получателем;
  - у остальных документов — со складом документа.

  `stock_transition` показывает перечень с описанием («склад-получатель: в
  документе «W», в движениях «W2»») и счётчик в «Итого», `check_costs` —
  перечень. Автоматически ничего не исправляется. Решение за человеком:
  перепровести документ в форме (движения примут его реквизиты) или вернуть
  документу реквизиты движений — тоже в форме.
- **Не входит в этап:** строки документа (закрыты следующим этапом, раздел
  ниже); вид оприходования или списания (`kind`); основание возврата;
  момент создания документа (`created_at` — не редактируется). Прямой SQL и
  `_base_manager` видит только диагностика.

### Строки проведённых документов (19.10.2026)

**Закрытый дефект.** Независимо воспроизведено на приёмке «1 шт. по 100».
Регрессионные тесты `apps/inventory/tests_posted_lines.py` до исправления
падали.

| Действие | Документ | Движение |
|---|---|---|
| `line.quantity = 2; line.save(update_fields=["quantity"])` | 2 шт. на 200 | 1 шт. на 100 |
| `line.delete()` | пусто | 1 шт. на 100 |

**Контракт** (`posting.py`, правило 10) — тот же `editing()`, без второго
механизма.

- Строки проведённого документа, а также документа, у которого остались
  движения, можно добавлять, менять и удалять только внутри `editing()`
  этого документа или самим `post()`. Защищены товар, количество, цена,
  скидка, НДС, серийные номера, связь строки возврата с исходной строкой,
  резервная стоимость и документ строки. После всех изменений документ
  перепроводится один раз.
- **Разрешение** выдаётся конкретному документу в текущей транзакции
  (`_document_scope`) вместе с уже заблокированными товарами:
  - новый или заменённый товар строки должен быть среди них —
    `editing(products=[…])`, форма передаёт товары своих строк. Иначе
    отказ «не заблокирован заранее», блокировки не добираются в обратном
    порядке;
  - строки другого проведённого документа внутри чужого `editing()` не
    меняются;
  - строки черновика внутри чужой операции меняются только по уже
    заблокированным товарам.
- **Отклоняются до записи** (`PostedChangeError`), и статус документа
  берётся из базы под блокировкой его строки, поэтому устаревший объект не
  проходит:
  - `save()` и `update_fields` (с именем поля или столбца), создание строки,
    `delete()`;
  - связанный менеджер — `create()`, `update_or_create()`, `add()`,
    `update()`, `all().delete()`; менеджер строк сделан базовым
    (`Meta.base_manager_name`), поэтому `add()` тоже проходит через защиту;
  - `QuerySet.update()` и `delete()` (выражение считается изменением);
  - `bulk_create()`, `bulk_update()`; `bulk_create(update_conflicts)` не
    поддерживается.
- **Перенос строки между документами** (смена документа строки,
  `add()`), если хотя бы один из них проведён, не поддерживается. Между
  черновиками — как обычно.
- **Строку, на которую ссылается строка проведённого возврата** (строка
  отгрузки-основания), удалить нельзя: «На документ ссылается проведённый
  возврат покупателя № … от …». Иначе связь пропала бы мимо перепроведения
  возврата. Раньше такое удаление проходило, если история оставалась
  корректной, а связь возврата молча обнулялась. Связь черновика возврата
  обнуляется как прежде.
- **Массовое удаление проведённых документов** (`QuerySet.delete()`
  документов) отклоняется: каскад удалил бы строки, а движения остались бы.
  `delete()` документа по одному, как прежде, снимает его с проведения.
- **Расчётные поля** — себестоимость строки отгрузки (`cost_*`) — пишет
  пересчёт, они не защищаются.
- **Форма** (несколько строк сразу), отмена проведения, удаление документа и
  админка (только черновики) работают как прежде. `fix_stock_history
  --link` меняет строку проведённого возврата через `editing()`, внутри
  отложенной проверки истории.
- **Миграции** `purchases.0006`, `sales.0009`, `inventory.0010`
  (`line_base_manager`) — только состояние моделей (базовый менеджер
  строк), SQL нет: откат и повтор проверены на копии.
- **Диагностика.** Существующая `check_costs` оба воспроизведённых
  расхождения видела: «ТРЕБУЕТ РЕШЕНИЯ — движения не сопоставляются со
  строками документа», и `stock_transition` тоже, в разделе «Другие
  проблемы». Она видела и смену товара, а смену цены или скидки — как
  расхождение стоимости приёмки. Не видела три вещи: добавленную строку,
  смену серийного номера в строке и смену связи строки возврата.
  `transition.line_mismatches()` теперь сравнивает количество товара в
  строках и в движениях по каждому направлению (у перемещения — расход и
  приход отдельно, услуги без движений не учитываются) и серийные номера
  строк с движениями номеров. `stock_transition` показывает перечень и
  счётчик в «Итого», `check_costs` — перечень. Без исправления.
- **Не входит в этап:**
  - вид оприходования или списания (закрыт следующим этапом, раздел ниже);
  - основание возврата в шапке;
  - смена связи строки возврата прямой записью в базу — её не видит
    никакая диагностика: «проведённая» связь нигде не хранится.

### Вид оприходования / списания (19.10.2026)

**Закрытый дефект.** Независимо подтверждено. У проведённого оприходования
1 шт. по 100 выполнили `kind = "expense"; save(update_fields=["kind"])`:
документ стал списанием, а движение осталось `adjustment_income` +1 на 100.
Регрессионный тест — `apps/inventory/tests_adjustment_kind.py`; до
исправления он падал.

**Согласованность с программой.** Вид задаётся только при создании, из
адреса страницы (`/stock/adjustments/income/new/` или
`/stock/adjustments/expense/new/`). В форме документа поля вида нет;
редактирование, проведение, отмена и удаление вид не трогают. Поэтому
пользователь в программе вид сменить не может, и контракт интерфейс не
затрагивает. Админка, как и прежде, правит только черновики. Нумерация —
своя серия у каждого вида: организация + вид + год.

**Контракт** (`posting.py`, правило 11; поле вида — `IDENTITY_FIELDS`).

- Вид документа нельзя менять, если документ проведён или у него есть
  движения, даже со статусом «черновик». Запрет действует и внутри
  `editing()` с перепроведением.
- Исправление ошибочного вида — штатная последовательность:
  1. отменить проведение — со всеми проверками зависимой истории, например
     запрета минуса;
  2. изменить вид черновика;
  3. провести заново.

  Старые движения убираются полностью, новые получают правильный знак.
- Вид, который записывается, сверяется со свежим состоянием базы под
  блокировкой строки документа. Отклоняются:
  - `save()` и `update_fields`;
  - устаревший объект;
  - выражение вместо значения.

  Массовая смена вида — `QuerySet.update()`, `bulk_update()`,
  `bulk_create(update_conflicts)` — не поддерживается даже у черновиков: их
  номер нужно проверить в серии нового вида.
- Проведение, отмена и удаление отклоняются с просьбой загрузить документ
  заново, если:
  - вид у объекта изменён без сохранения или объект устарел;
  - движения документа записаны другим видом.

  Так не выбирается неверный тип движений.
- **Правило номера.** При смене вида черновика номер сохраняется. Он
  регистрируется в серии нового вида: счётчик этой серии становится не
  меньше номера. Счётчик прежней серии не уменьшается, там остаётся
  пропуск. Если такой номер в серии нового вида за тот же год уже занят,
  смена вида отклоняется целиком — вид, номер и счётчики прежние. Можно
  указать другой номер или оставить поле пустым, и тогда номер будет
  следующим в новой серии. Сохранение одного комментария нумерацию не
  трогает.
- **Диагностика.** До этапа `check_costs` такого расхождения не видел
  («Расхождений нет»). Сверка строк прошлого этапа видела его лишь
  косвенно — «расход: в строках 1, в движениях 0» — и советовала
  перепровести. Для этого случая совет неверен: перепроведение не убрало
  бы движения прежнего вида. Теперь `transition.kind_mismatches()`
  находит обе стороны: списание с движениями оприходования и наоборот.
  `stock_transition` показывает перечень, решение и счётчик в «Итого»,
  `check_costs` — перечень; сверка строк такие документы пропускает.
  Автоматически ничего не исправляется.
- **Исправление расхождения** — решение человека. Документу возвращают
  вид его движений (`kind = …; save(update_fields=["kind"])`): это
  единственная смена вида, допустимая у документа с движениями, и она тоже
  проходит проверку номера. Дальше при необходимости — штатная
  последовательность.
- **Не входит в этап:** основания возвратов (закрыты следующим этапом,
  раздел ниже), другие реквизиты, интерфейс. Номер проведённого документа
  по-прежнему не защищён: в движениях хранится его копия для показа.

## 1. Подтверждённый риск

Организация А приняла на склад W 1 шт. по 100. У организации Б поступлений
нет, минус ей запрещён. Б отгружает со склада W этот товар — **отгрузка
проводится**, себестоимость 100, общий остаток W становится 0. После этого
А **не может продать свою единицу**: «Недостаточно товара».

Причина: остаток (`StockBalance`), движения (`StockMovement`), покрытия
дефицита и серийные номера не знают организацию; ключ учёта — «товар +
склад». Организация есть только у документа. Сквозная проверка
(`docs/end-to-end-check.md`) этого не обнаружила: у второй организации там
был свой склад.

Цены продажи не влияют на себестоимость; «себест.» — себестоимость строки
отгрузки, «не покр.» — непокрытое (проданное раньше поступления) количество.

**Где сейчас хранится принадлежность серийного номера:** `SerialNumber.warehouse`
и `status` (на складе / продан / возвращён / списан) и журнал `SerialMovement`
(документ, дата, склад, ±1). **Организации нет ни в номере, ни в его
движениях.** Проверки `serials.apply` сравнивают только склад: расход и
перемещение разрешены, если номер лежит на складе документа, — чей он, не
проверяется. Ввод номеров для уже лежащего товара (`serial_stock`, без
документа) тоже не указывает организацию.

**Одновременные операции (PostgreSQL, сейчас).** А и Б одновременно отгружают
единственную единицу А. Вторая операция ждала блокировку товара (проверено по
`pg_stat_activity`). Порядок А → Б: А проведено, Б — отказ. Порядок Б → А:
**Б проведено (себест. 100), А — отказ.** Исход определяется порядком; по
предложению при любом порядке — А проведено, Б отказ.

## 3. Целевая модель

- Склад — физическое место; на нём лежат товары разных организаций.
- Количество, стоимость, средняя и дефицит — по ключу **«организация + склад +
  товар»**. Организация движения — организация документа-источника.
- Поступление покрывает дефицит только своей организации (и своего склада).
- Перемещение — документ одной организации: расход и приход с её ключами;
  берёт только положительный остаток своей организации на складе-отправителе
  (правило `transfer_deficit` — уже действует, но по общему ключу).
- Передачи товара другой организации через перемещение нет. Передача между
  организациями — отдельная явная операция (раздел 11, решение 5).
- Возврат покупателя по основанию — только той же организации (уже
  проверяется `return_limits.check_return`); без основания — по средней
  ключа своей организации. Возврат поставщику — по средней своей организации.
- Запрет минуса применяется к ключу по флагу **организации ключа**, а не
  организации операции (важно при отмене документа и смене организации).
- Серийный номер принадлежит организации: расходовать и перемещать его может
  только она.
- Денежные расчёты и взаиморасчёты уже разделены по организациям — не меняются.

| Остатки на дату `costing.state_on`, `BalanceListView` | по складам | по ключу; фильтр организации |
| Подбор товара в документах (`catalog.api._stock_map`), карточка товара (`catalog.views._serial_stock`) | остаток склада по всем организациям | остаток организации документа на складе; в карточке — по организациям |
| Отчёт «Продажи и прибыль», сводка на главной | все организации вместе, фильтра нет | фильтр организации (раздел 8) |
| `check_costs`, `fix_stock_history` | расхождения по складам | по ключу; плюс разбор переноса (раздел 7) |
| Админка остатков и движений (только чтение) | — | показать организацию |
| Блокировки `services.lock_products`, `document_edit._lock_products` | строка документа → товары по возрастанию id | без изменений (раздел 9) |

## 5. Схема и миграции (план, не создавались)

1. `inventory.0007_organization_fields` — поля `organization` (FK, пока
   NULL допускается) у `StockMovement`, `StockBalance`, `SerialNumber`,
   `SerialMovement`; индекс движений (товар, организация, склад).
2. `inventory.0008_fill_organization` (перенос данных) — организация каждого
   движения и движения номера **из документа-источника** (`doc_type` +
   `doc_id` → приёмка, отгрузка, возвраты, перемещение, оприходование,
   списание). Если документа нет или он не проведён, а движения есть, —
   организация **остаётся пустой** (требует решения), по умолчанию не
   ставится. Ввод номеров остатка (`serial_stock`) — пусто, требует решения.
   Организация номера — по его последнему движению.
3. `inventory.0009_balance_key` — снять уникальность (товар, склад),
   поставить (организация, товар, склад). Строки `StockBalance` — кэш:
   миграция их удаляет, пересчёт строит заново по ключам. Себестоимость
   миграция не считает.
4. Сразу после миграций при закрытом доступе — пересчёт
   (`check_costs --apply --i-have-a-backup`): остатки, стоимость, покрытия и
   себестоимость отгрузок из истории документов. До пересчёта остатков нет —
   отгрузки отклоняются («недостаточно товара»), а страница остатков должна
   предупреждать «остатки не пересчитаны после обновления». Это безопасный
   отказ, а не неверные числа.
5. Документы продаж, закупок и денег — без изменений схемы (организация в
   них уже есть).
6. Обратные миграции: снимают поля и возвращают ключ (товар, склад);
   **решения людей по движениям без источника и номерам теряются**, остатки
   нужно пересчитать прежним кодом.

## 6. Нужные проверки при внедрении

- Перенос сценариев раздела 2 в тесты на настоящих документах с ручными
  числами (колонка «Предложение»); на прежнем коде они должны падать.
- Отмена и перепроведение, смена организации проведённого документа (оба
  ключа), удаление документа.
- Серийные номера: расход, перемещение, возврат, ввод остатка — по
  организации.
- Остатки на дату по организациям; итог «все организации» = сумма.
- Отчёт «Продажи и прибыль» и сводка: фильтр и сумма по организациям.
- Деньги и взаиморасчёты: прежние тесты без изменения ожиданий.
- Одновременные операции (раздел 9).
- Перенос: миграции на копии старой схемы, пустые организации, отчёт
  до/после.

## 7. Перенос старых данных

Принципы (как просили): организация движения — **из документа-источника**;
отсутствующие и неоднозначные — «требует решения», без организации по
умолчанию; общий старый остаток **не делится**: остатки и стоимость
получаются пересчётом истории документов по новым ключам.

**Диагностика до перехода** — прототип: `org_stock_current.py --existing`
(только чтение). Показывает:

1. сколько движений, документов-источников и организаций; движения без
   документа, у непроведённых документов, номера без документа;
2. товары и склады со смешанной историей нескольких организаций;
3. сверку: модель «как сейчас» повторяет записанные суммы движений;
4. **отгрузки, у которых изменится себестоимость или непокрытое
   количество** («было → станет»);
5. **новые нарушения**: остаток организации с запретом минуса уходит в минус
   (ранее допустимая отгрузка становится дефицитом или нарушением),
   перемещение чужого товара;
6. изменение прибыли «Продажи и прибыль» по месяцам.

Результаты:

| Данные | Источники | Требует решения | Смешанные склады | Изменится себестоимость | Новые нарушения | Прибыль |
|---|---|---|---|---|---|---|
| Сценарии раздела 2 (две организации) | 31 документ | 0 | 10 товаров | 12 отгрузок (например, 750 → 500, 100 → 0 с дефицитом 1) | 11 (9 — минус у организации с запретом; 2 — перемещение чужого товара) | октябрь 2026: +1 370 |
| Копия локальной базы разработки (после миграций) | 7 документов, 1 организация | 0 | нет | 0 | 0 | без изменений |

Модель «как сейчас» совпала с записанными суммами: 31 из 31 и 8 из 8.
Флаги «минус разрешён» берутся текущие (на момент разбора).

**Порядок переноса на сервере** (дополнение к `docs/release-readiness.md`,
раздел 7): резервная копия → диагностика на восстановленной копии
(разбор выше) → решения по «требует решения» и новым нарушениям →
миграции при закрытом доступе → пересчёт → повторная диагностика
(«Расхождений нет», нарушения — только принятые решениями) → отчёт
«Продажи и прибыль» до/после по месяцам и организациям сохранить →
открыть доступ.

## 8. Фильтры и отчёты

- **Остатки** (текущие и на дату): фильтр «Организация». Строка —
  организация + товар + склад: количество, стоимость, средняя этой
  организации. Режим «все организации» — строки по каждой организации и
  итог; если нужна строка «товар + склад» по всем — количество и стоимость
  **складываются**, средняя = сумма стоимостей ÷ сумма количеств (не
  отдельный «общий» расчёт).
- **«Продажи и прибыль»** и сводка на главной: фильтр по организации
  отгрузки и возврата. Итог по всем организациям — сумма строк, посчитанных
  по своим организациям (себестоимость каждой строки уже своя).
- **Подбор товара в документе** показывает остаток организации документа.
- **Деньги и взаиморасчёты** уже по организациям — без изменений поведения.

## 9. Одновременные операции

**Порядок блокировок не меняется и не ослабляется:** строка документа →
товары по возрастанию id (`lock_products`, FOR NO KEY UPDATE) → пересчёт
товара целиком (все организации и склады) → денежные уровни, как сейчас.
Блокировка по товару строже, чем по «организация + товар»: она покрывает
смену организации документа (оба ключа — один товар) и любые перемещения.
Более мелкая блокировка (организация + товар) возможна позже как
оптимизация, но потребует блокировать оба ключа при смене организации и не
даст выигрыша в корректности — в первом этапе не предлагается.

Проверки для PostgreSQL (доказательство ожидания — `run_overlapping`, точка
остановки — после блокировок, например `services.check_history`):

1. А и Б одновременно отгружают с общего склада единицу А — при обоих
   порядках: А проведено, Б отказ; остаток А 0. Сейчас — по порядку
   (воспроизведено выше).
2. Б принимает товар, одновременно А (минус разрешён) отгружает в дефицит —
   приёмка Б не покрывает дефицит А ни при каком порядке.
3. Две отгрузки одной организации последней единицы — одна отказ (прежняя
   гарантия, существующие тесты).
4. Смена организации проведённой приёмки одновременно с отгрузкой из неё —
   одна операция ждёт другую; итог: либо отгрузка отклонена, либо смена
   организации.
5. Две организации одновременно перемещают или продают один серийный
   номер — проводится только операция владельца.
6. Перемещение А W1 → W2 одновременно с отгрузкой А с W1 — остаток не
   уходит в минус.
Все существующие тесты одновременных операций (склад и деньги) — без
изменения ожиданий.

## 10. Не входит в первый этап

Передача товара между организациями (межфирменная продажа), закрытие
периодов, разница стоимости возврата поставщику, отложенные ошибки
интерфейса (выбор контрагента, подстановка товара).

## 11. Нерешённые случаи (нужно решение владельца учёта)

1. **Старые продажи чужого товара** (Б продала единицу А, сценарии 1, 2, 7):
   после разделения у Б — дефицит (себестоимость предварительная), у А —
   остаток, которого физически нет. Варианты: оформить задним числом
   передачу между организациями; поменять организацию отгрузки на А, если
   это ошибка ввода; оставить дефицит Б до её поступления.
2. **Старые перемещения чужого товара** (сценарий 6): после разделения —
   нарушение `transfer_deficit`, операции с товаром будут отклоняться, пока
   не исправлено. Варианты: сменить организацию перемещения; оформить
   передачу между организациями.
3. **Номера, введённые как остаток** без документа: чьи? Предлагаемое
   правило (на согласование): однозначно, если на складе на дату ввода
   остаток без номеров был только у одной организации; иначе — решение
   человека.
4. **Старый минус у организации с запретом** после разделения: сейчас
   прежний минус операции не блокирует (запрещено только его углубление).
   Оставить так или блокировать товар до исправления?
5. **Передача товара между организациями**: перемещением — нельзя. Нужен ли
   отдельный документ (и как он отражается во взаиморасчётах между своими
   организациями)?
6. **Инвентаризация общего склада**: излишек на полке — чей? Документ
   оприходования уже требует организацию; правило выбора — за человеком.
7. **Отчёты по умолчанию**: показывать все организации или организацию по
   умолчанию (главная, «Продажи и прибыль», остатки)?
8. **Возврат без основания у организации без истории товара**: оценка
   по последней средней своей организации, иначе по цене, зафиксированной в
   строке (как сейчас для склада). Себестоимость таких возвратов может
   измениться — она входит в отчёт до/после.
