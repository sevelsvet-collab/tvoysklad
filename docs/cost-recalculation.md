# Себестоимость: правила расчёта и проверка существующих данных

## Как считается себестоимость

Метод — средневзвешенная себестоимость по складу. Расчёт ведёт
`apps/inventory/costing.py`: он проигрывает всю историю товара (по всем складам
сразу) в хронологическом порядке и согласованно записывает результат в
движения (`StockMovement.amount`, `cost`), строки отгрузок
(`ShipmentLine.cost_amount`, `cost_price`) и остатки (`StockBalance.value`,
`avg_cost`).

**Деньги хранятся суммами.** Учётная величина — сумма в копейках: стоимость
остатка и сумма каждого движения. Цена единицы (`cost`, `cost_price`,
`avg_cost`) — производная «сумма ÷ количество», округлённая для показа; итоги
из неё не вычисляются. Стоимость остатка всегда равна сумме приходов минус
сумма расходов, копейка в копейку. Итоги отгрузки, прибыль в отчёте и
стоимость остатков берутся из записанных сумм.

**Порядок операций** один для себестоимости и для проверки наличия: дата
документа → время документа → момент создания документа → тип и id документа →
порядок строк. Момент проведения в порядок не входит, поэтому перепроведение
документ не переставляет. Форма документа показывает время без секунд, но
хранит их и при сохранении не обрезает.

| Операция | Сумма движения |
|---|---|
| Приёмка | сумма строки документа со скидкой поставщика |
| Оприходование | количество × цена из документа |
| Отгрузка, возврат поставщику, списание, расход перемещения | доля стоимости остатка перед операцией: стоимость × количество ÷ остаток, до копейки (половина — вверх). Расход всего остатка списывает всю оставшуюся стоимость. Сверх положительного остатка (минус разрешён) — см. «Продажа раньше поступления» |
| Приход перемещения | та же сумма, что у расхода этого перемещения |
| Возврат покупателя с отгрузкой-основанием | по строке отгрузки: сначала гасит её непокрытые единицы (сумма 0), затем восстанавливает долю определённой себестоимости строки нарастающим итогом: база = отгружено − погашено, восстановлено round(С × R ÷ база); полный возврат восстанавливает ровно С. Серийный товар без указанной строки — по номерам, каждый номер в свою строку. Строка неизвестна, а строк товара несколько — «по отгрузке в целом»: С и база — по всем этим строкам. В одной группе «отгрузка + товар» только один из двух способов |
| Возврат покупателя без основания | по средней на складе возврата перед операцией → по последней известной средней этого склада → по цене, зафиксированной в строке возврата |

**Продажа раньше поступления** (когда организации разрешён минус; правило
согласовано владельцем — `docs/negative-stock-proposal.md`). Расход сверх
положительного остатка забирает весь остаток и всю его стоимость, а
недостающие единицы становятся дефицитом этой строки
(`StockMovement.open_qty`, `ShipmentLine.cost_open_qty`): их себестоимость
ещё не определена и в суммы не входит, прибыль отгрузки — предварительная.
Любое следующее поступление на этот склад (приёмка, оприходование, приход
перемещения, возврат) сначала покрывает дефициты в порядке расходов; доля
суммы — нарастающим округлением по его единицам, остальное — в остаток.
Каждое покрытие записывается (`DeficitCover`). При количестве ≤ 0 стоимость
остатка ровно 0. Пример: приход 1 на 100,00 → отгрузка 2 (100,00 + 1 шт.
без себестоимости) → приход 2 на 300,00 → отгрузка 250,00, остаток 1 на
150,00.

**Ограничения итоговой истории.** Операция отклоняется целиком (документ,
строки, движения, суммы, остатки не меняются), если после неё в истории
товара: перемещение забирает больше положительного остатка отправителя на
свой момент (независимо от разрешения минуса); возврат на другой склад
затрагивает непокрытые единицы строки отгрузки; возврат без указанной строки
при нескольких строках товара в основании, у части которых дефицит; по одной
отгрузке и товару есть и возвраты по строкам, и возвраты без строки
(`return_mixed`: одни и те же единицы восстановили бы стоимость дважды —
уточнить нужно возврат без строки); движения не сопоставляются со строками;
возврат ссылается на негодное основание.
Проверяется проведение, отмена, удаление, уменьшение и перенос любого
документа, в том числе более раннего.

Следствия: последний расход забирает остаток округления; несколько частичных
отгрузок в сумме списывают ровно столько же, сколько одна полная; перемещение
по цепочке складов стоимость не теряет. Пример: три единицы на 100,00,
проданные по одной, получают 33,33 + 33,34 + 33,33.

**Приёмка.** В стоимость остатка входит сумма строки документа целиком
(`ReceiptLine.total`, с учётом скидки), а не «количество × округлённая цена».
НДС учитывается как раньше: цена берётся из документа как есть.

**Возврат без основания.** При первом проведении в строке возврата
запоминается закупочная цена карточки на этот момент
(`CustomerReturnLine.fallback_cost`). Пересчёт берёт её из строки; текущая
цена карточки в расчёте не участвует. Отмена и повторное проведение значение
не меняют; оно сбрасывается, только если в строке заменили товар.

**Возврат с основанием.** Отгрузка-основание должна быть проведена, стоять в
хронологии раньше возврата и содержать товар. Иначе проведение возврата
отклоняется с объяснением. Так же отклоняется отмена, удаление или перенос
отгрузки, на которую ссылается проведённый возврат. Возврат не превращается
в «без основания» молча — основание нужно убрать из документа явно.

**Проверка наличия.** Если минус запрещён, остаток проверяется после каждой
операции в хронологии, а не на конец дня: отгрузку от 11:00 нельзя провести
при приёмке от 12:00 того же дня. Минус, существовавший раньше, операции не
блокирует, пока операция не создаёт новый минус и не углубляет прежний ни в
одной точке хронологии.

Округление: суммы — до копейки, половина — вверх. Цена единицы для показа
округляется так же и в расчётах не участвует.

Пересчёт запускается сам при проведении, перепроведении, отмене и удалении
любого складского документа — для всех товаров документа, в той же транзакции
и под той же блокировкой товара.

## Старые данные: что переносится и что нет

- **Порядок.** Миграция `inventory.0004` копирует в движения время и момент
  создания документов. Себестоимость и остатки она не трогает.
- **Точные суммы.** Миграции `inventory.0005` и `sales.0007` добавляют поля
  сумм пустыми и ничего не пересчитывают. Пока товар не пересчитан, итоги
  по нему показываются по-старому («количество × округлённая цена»). Суммы
  заполняет пересчёт — из исходных документов, а не из округлённой цены.
  Диагностика различает два случая: старый расчёт совпадает с точным («сумма
  ещё не записана») и не совпадает (настоящее расхождение в деньгах — оно
  показано как «в базе (цена, сумма) → по расчёту (цена, сумма)»). Для
  движений, которые нельзя однозначно сопоставить со строкой документа,
  точную сумму взять неоткуда: остаётся «количество × записанная цена», а
  документ попадает в раздел «ТРЕБУЕТ РЕШЕНИЯ».
- **Ссылка движения на строку.** Новые движения помнят строку документа. Старые
  сопоставляются со строкой, только если это однозначно: у документа ровно
  одна свободная строка этого товара с таким количеством и ровно одно такое
  движение. Иначе движение не угадывается: его себестоимость остаётся
  записанной, строка документа не меняется, диагностика требует решения.
  Решение — открыть документ в программе и сохранить (перепровести).
- **Скидка в старых приёмках.** Раньше приход шёл по цене без скидки.
  Диагностика сравнивает движение с исходной строкой приёмки и показывает
  разницу в отдельном разделе.
- **Старые возвраты без основания.** Миграция `sales.0006` переносит в строку
  возврата стоимость старого движения (пометка `legacy`) — это фактическая
  стоимость, по которой возврат был оприходован; какой была цена карточки на
  тот день, неизвестно. Диагностика помечает такие возвраты как
  неопределённость, если это значение реально используется. Где перенос
  неоднозначен, строка остаётся без значения, стоимость движения не меняется.
  Перепроведение такого возврата зафиксирует цену карточки на момент
  перепроведения — решить, что с ним делать, нужно до этого.
- **Старые возвраты с негодным основанием и другие проблемы «ТРЕБУЕТ
  РЕШЕНИЯ»** (в том числе V1–V3 выше) блокируют операции с этим товаром:
  каждая отклоняется с перечнем мешающих документов. Проходит только
  исправляющая операция — после которой история товара корректна (снять с
  проведения или изменить названный документ). Если мешающих документов
  несколько и по одному их не исправить, — команда `fix_stock_history`
  (см. ниже). Даты и суммы автоматически не исправляются.
- **Дефицит и покрытия** (миграция `inventory.0006`): поля непокрытого
  количества добавляются нулевыми, таблица покрытий — пустой. Их заполняет
  исправление `check_costs --apply`; старые отгрузки «в минус» получают
  себестоимость по новому правилу. Диагностика показывает сводку по месяцам
  продажи: в базе / по расчёту — прибыль каких периодов изменится.
- **Связь строки возврата со строкой отгрузки** (миграция `sales.0008`)
  восстанавливается только однозначно: в основании одна строка этого
  товара, или серийный товар, номера которого есть только в одной строке.
  Остальные возвраты остаются без связи; при дефиците у части строк это
  «ТРЕБУЕТ РЕШЕНИЯ», иначе — замечание (себестоимость восстанавливается по
  строкам в целом).

## Ограничения

- **Продажа раньше поступления: закрытия периодов нет.** Поступление
  уточняет себестоимость прошлой продажи задним числом — меняется прибыль
  месяца продажи. Пока дефицит не покрыт, себестоимость этих единиц не
  определена (0 с пометкой «предварительная»), а не оценена.
  (Прежнее правило — «расход из пустого склада по 0, сверх остатка по
  средней на всё количество, приход на минус завышает следующую партию» —
  заменено; стоимость сохраняется и при минусе.)
- **Остатки на дату** (`Остатки → на дату`) проигрывают историю каждого
  товара до выбранной даты отдельно; на большой базе страница может
  открываться медленно.
- **Цена единицы — для показа.** При дробных количествах показанная цена
  может отличаться на копейку от средней (сумма 43,75 за 0,5 шт. показывается
  как 87,50 при средней 87,49). Итоги считаются из сумм.
- **Серийные номера** по-прежнему проверяются по дням: у движения серийного
  номера есть только дата.
- **Возврат больше отгруженного** теперь отклоняется (см. `docs/returns.md`).
  Старые превышения остаются в базе, пока их не исправят вручную; стоимость
  по ним считается линейно от себестоимости отгрузки.
- **Документы одной минуты.** Форма принимает время с точностью до минуты.
  Если время изменить вручную, секунды становятся нулевыми; при совпадении
  времени порядок определяет момент создания документа.
- **Отчёт «Продажи и прибыль»** (с 16.10.2026) вычитает возвраты
  покупателей: выручку — по сумме возврата, себестоимость — по сумме,
  восстановленной движением возврата; возврат — в периоде возврата
  (`docs/sales-report.md`).
- **Скорость.** Каждая операция проигрывает всю историю товара.
- Платежи пересчёт не затрагивает.

## Обновление программы: сначала копия, потом пользователи

После обновления обычное проведение любого документа пересчитывает всю
историю его товаров по новым правилам. Старые цифры по товару изменятся при
первой же операции с ним. Кроме того, документы, которые новая проверка
наличия считает нарушением (расход раньше прихода в тот же день), нельзя
будет перепровести без исправления времени. Поэтому диагностика выполняется
на копии базы до того, как пользователей пустят в новую версию.

1. Закрыть доступ пользователям (остановить `sklad-web` или закрыть сайт).
2. Сделать резервную копию и убедиться, что файл не пустой:

   ```bash
   cd /opt/sklad
   docker compose -f docker-compose.behind-proxy.yml exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -Fc "$POSTGRES_DB"' > backup_before_costs_$(date +%F).dump
   ls -lh backup_before_costs_*.dump
   ```

3. Развернуть копию в отдельной базе и работать только с ней:

   ```bash
   docker compose -f docker-compose.behind-proxy.yml exec -T db sh -c 'createdb -U "$POSTGRES_USER" sklad_check'
   docker compose -f docker-compose.behind-proxy.yml exec -T db sh -c 'pg_restore -U "$POSTGRES_USER" -d sklad_check' < backup_before_costs_ДАТА.dump
   ```

   Дальше команды новой версии запускаются с `DATABASE_URL`, указывающим на
   `sklad_check` (те же логин, пароль и хост, другое имя базы), и **в обход
   entrypoint** (`--entrypoint python`): иначе перед командой контейнер
   выполнит свои миграции и `collectstatic` в общий с рабочим приложением том
   статики. Вариант без ввода пароля и с проверкой имени базы — в
   `docs/release-readiness.md`, раздел 7:

   ```bash
   docker compose -f docker-compose.behind-proxy.yml run --rm --no-deps --entrypoint python -e DATABASE_URL=postgres://ЛОГИН:ПАРОЛЬ@db:5432/sklad_check web manage.py migrate
   docker compose -f docker-compose.behind-proxy.yml run --rm --no-deps --entrypoint python -e DATABASE_URL=postgres://ЛОГИН:ПАРОЛЬ@db:5432/sklad_check web manage.py check_costs --limit 0 > costs_before.txt
   ```

4. Прочитать `costs_before.txt`:
   - «Стоимость поступлений не совпадает со строкой приёмки» — старые приёмки
     со скидкой; после исправления себестоимость и прибыль по ним изменятся;
   - строки «по расчёту 0.00» у отгрузок — отгрузка стоит раньше прихода по
     времени документа; исправить время документа в программе;
   - «ТРЕБУЕТ РЕШЕНИЯ» — товар не будет исправлен, пока документ не приведён
     в порядок (перепровести документ; у возврата — исправить или убрать
     основание);
   - «НЕОПРЕДЕЛЁННОСТЬ» — возвраты, исходная стоимость которых не сохранилась;
     значение оставлено, проверить вручную.
5. На копии же применить исправление и проверить результат:

   ```bash
   docker compose -f docker-compose.behind-proxy.yml run --rm --no-deps --entrypoint python -e DATABASE_URL=postgres://ЛОГИН:ПАРОЛЬ@db:5432/sklad_check web manage.py check_costs --apply --i-have-a-backup > costs_applied.txt
   docker compose -f docker-compose.behind-proxy.yml run --rm --no-deps --entrypoint python -e DATABASE_URL=postgres://ЛОГИН:ПАРОЛЬ@db:5432/sklad_check web manage.py check_costs --limit 0
   docker compose -f docker-compose.behind-proxy.yml run --rm --no-deps --entrypoint python -e DATABASE_URL=postgres://ЛОГИН:ПАРОЛЬ@db:5432/sklad_check web manage.py test apps.inventory.tests_concurrency
   ```

   Повторная проверка должна показывать только то, что требует решения
   человека. Количества в остатках измениться не должны. Тесты конкуренции
   создают и удаляют собственную базу `test_sklad_check`.
6. Только после этого решать, обновлять ли рабочую базу: обновить программу,
   выполнить миграции, запустить `check_costs` (без `--apply`) и сравнить вывод
   с полученным на копии. Исправляющий режим на рабочей базе — отдельное
   решение, после резервной копии:

   ```bash
   docker compose -f docker-compose.behind-proxy.yml exec -T web python manage.py check_costs --apply --i-have-a-backup
   ```

7. Открыть доступ пользователям. Удалить проверочную базу:

   ```bash
   docker compose -f docker-compose.behind-proxy.yml exec -T db sh -c 'dropdb -U "$POSTGRES_USER" sklad_check'
   ```

Откат — восстановление из копии:

```bash
docker compose -f docker-compose.behind-proxy.yml exec -T db sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists' < backup_before_costs_ДАТА.dump
```

## Пакетное исправление истории: fix_stock_history

Когда операции с товаром блокирует несколько документов сразу и снимать их
по одному нельзя (каждая промежуточная история тоже некорректна):

    python manage.py fix_stock_history --unpost transfer:12 --unpost customer_return:40
    python manage.py fix_stock_history --unpost transfer:12 --unpost customer_return:40 --apply --i-have-a-backup

Типы: shipment, customer_return, receipt, supplier_return, transfer,
adjustment. `--repost ТИП:ID` перепроводит документ по его текущим строкам.
`--link СТРОКА_ВОЗВРАТА:СТРОКА_ОТГРУЗКИ` (id из сообщения диагностики)
указывает в строке возврата покупателя строку отгрузки и перепроводит
проведённый возврат — так уточняют сразу несколько старых возвратов без
строки. Строку выбирает человек; команда проверяет только, что это строка
той же отгрузки с тем же товаром.
Все операции выполняются в одной транзакции, итоговая история проверяется
один раз в конце. Без `--apply` всё откатывается: команда только сообщает,
останутся ли проблемы. С `--apply` результат записывается, только если
проблем не осталось; иначе не меняется ничего. Остальные проверки
документов (запрет минуса, серийные номера, количество возвратов) действуют
как обычно; даты и суммы документов команда не меняет.

## Как работает исправляющий режим

- Без `--apply` команда только читает.
- `--apply` требует второго ключа `--i-have-a-backup`.
- Единица исправления — товар: одна транзакция под блокировкой товара. Если у
  товара есть проблема, требующая решения, для него не записывается ничего —
  ни движения, ни строки, ни остатки; команда перечисляет такие товары.
- Повторный запуск безопасен: второй раз команда ничего не меняет.
