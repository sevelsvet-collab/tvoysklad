# Взаиморасчёты с контрагентами — уточнённое предложение

Статус: **первый этап реализован 18.10.2026** (раздел «Реализовано» ниже).
Рабочие данные, сервер и `.env` не трогались. Заменяет первую версию этого
документа: правило «деньги относятся к стороне, по которой есть документы»
снято.

## Реализовано (18.10.2026)

- **Платёж:** поле «Назначение для взаиморасчётов»
  (`Payment.settlement_purpose`): оплата от покупателя, возврат покупателю,
  оплата поставщику, возврат от поставщика, не распределено. Текстовое
  «Назначение платежа» не заменяет. Проверки (`services.purpose_errors`, в
  составе проверки связей платежа): назначение подходит к направлению денег;
  платёж по счёту покупателю — только «оплата от покупателя». Пустое значение
  у нового платежа («не указано») определяется при записи: со счётом —
  оплата от покупателя, без счёта — не распределено; «на основании счёта» —
  оплата от покупателя сразу. **Явно выбранное или уже записанное назначение
  молча не меняется** — противоречие показывается ошибкой (например, привязка
  счёта к записанному платежу «не распределено»). Проверки работают при
  `save()` (по тому, что будет записано: `update_fields`, устаревший объект,
  смена вида платежа), в форме и админке (`clean`), в `update`,
  `bulk_update`, `bulk_create` (пустое назначение там нужно указать явно,
  выражения отклоняются); снятие с проведения разрешено всегда. Последняя
  граница — ограничение базы (`finance_payment_settlement_purpose_valid`).
  Появление, отмена и изменение продаж и закупок назначение не меняют.
- **Корректировка взаиморасчётов:** поле «Сторона расчётов»
  (`SettlementCorrection.side`): продажи / закупки / не распределено. В
  форме новой корректировки сторона выбирается явно. Знак — по направлению
  (`settlement_effect`): по продажам «контрагент должен нам» увеличивает долг
  покупателя; по закупкам «мы должны» увеличивает наш долг.
- **Миграции:** `finance.0004_settlement_purpose_and_side` (поля и перенос:
  входящий платёж с действительной ссылкой на счёт покупателю — той же
  организации и того же покупателя — «оплата от покупателя», остальные
  платежи — «не распределено», корректировки — «не распределено»; тип
  контрагента, текст и наличие закупок не используются),
  `finance.0005_settlement_constraints` (ограничения базы).
- **Единый расчёт** `apps/finance/settlements.py` (только чтение): пары
  «организация + контрагент», по продажам, по закупкам, нераспределённые
  документы списком, справочная разница, пояснения (долг, аванс или
  переплата, встречные требования без зачёта, «нулевая разница — не значит,
  что всё оплачено»), справочные показатели счетов. Предварительно — **при
  наличии** нераспределённых документов, а не по их сумме. Отчёт
  «Взаиморасчёты» и вкладка «Документы» карточки контрагента используют его
  оба; итоги — «покупатели должны нам», «мы должны покупателям (авансы)»,
  «мы должны поставщикам», «поставщики должны нам (авансы)», «не
  распределено» — без сведения в одно число. В список документов карточки
  добавлены корректировки взаиморасчётов.
- **Диагностика** `manage.py check_settlements` (только чтение): прежний
  отчёт и новый расчёт по каждому контрагенту, документы для ручного
  уточнения с подсказкой (подсказка ничего не меняет), платежи с
  несовместимым назначением. Прежняя формула отчёта сохранена в
  `settlements.previous_report` только для этого сравнения.
- **Независимая модель** исправлена: две корректировки без стороны «он
  должен 100» и «мы должны 100» давали `final=True`. Теперь
  предварительность — по наличию нераспределённых документов, они
  перечисляются даже при нулевой сумме (регрессионная проверка
  `zero_sum_unallocated_stays_preliminary`; при прежнем правиле она падает).
  32 проверки.
- **Проверки:** `apps/finance/tests_settlements.py` — 51 тест: сценарии
  модели на настоящих документах, счёт без отгрузки, отгрузка без счёта,
  частичная отгрузка, авансы и возвраты, две организации, покупатель-
  поставщик, назначение во всех путях записи, форма, «на основании счёта»,
  уточнение назначения (сумма, касса и оплата счёта не меняются), отмена и
  повторный расчёт, отказ без частичной записи, чтение без записи, карточка,
  диагностика, миграция старой схемы (`MigrationExecutor`: finance 0003 →
  последняя), одновременная привязка счёта и смена назначения (PostgreSQL).
  `docs/proposals/settlements_current.py` теперь сравнивает прежний отчёт,
  независимый расчёт предложения и программу во всех 10 сценариях
  (`settlements_current_output.txt`; вывод до реализации —
  `settlements_current_before_output.txt`).

Не входит (как и было предложено): автоматический взаимозачёт,
договорной учёт, бухгалтерские проводки, закрытие периодов, привязка
платежей к конкретным отгрузкам.

Числа получены:

- независимой моделью без Django — `docs/proposals/settlements_model.py`
  (32 проверки с ручными ожидаемыми числами, с 18.10.2026 — с исправленной
  предварительностью; вывод — `settlements_model_output.txt`);
- настоящими документами во временной базе —
  `docs/proposals/settlements_current.py` (10 сценариев: прежний отчёт,
  это предложение и, с 18.10.2026, расчёт программы; вывод —
  `settlements_current_output.txt`, до реализации —
  `settlements_current_before_output.txt`; ключ `--existing` — разбор
  платежей копии данных, только чтение; основная диагностика теперь —
  `manage.py check_settlements`).

## Основа (без изменений)

- Задолженность — по проведённым отгрузкам, приёмкам, возвратам, платежам и
  корректировкам. Выставленный счёт задолженность не создаёт; «выставлено»,
  «оплачено по счёту», «отгружено по счёту» — показатели счёта.
- Расчёт — отдельно по паре «наша организация + контрагент». Документы
  организации А не гасят долги перед организацией Б. Сводка показывает
  «нам должны» и «мы должны» отдельно, без сведения в одно число.

## Назначение платежа

Направление денег не говорит, что именно оплачено. Одинаковый входящий
платёж 300 при одних и тех же документах (отгрузили 1000; приняли товар на
500, уплатили поставщику 800):

| Назначение | Он должен нам (продажи) | Мы должны ему (закупки) | Разница |
|---|---|---|---|
| «оплата от покупателя» | 700 | −300 (аванс поставщику) | 1000 |
| «возврат от поставщика» | 1000 | 0 | 1000 |

Одинаковый исходящий платёж 200 (отгрузили 1000, покупатель заплатил
1200; приняли товар на 500, не оплачен):

| Назначение | Продажи | Закупки | Разница |
|---|---|---|---|
| «оплата поставщику» | −200 (переплата покупателя) | 300 | −500 |
| «возврат покупателю» | 0 | 500 | −500 |

Разница одинаковая, задолженности — разные. Снятое правило к тому же
переписывало смысл старых платежей при появлении новых документов: у
покупателя (отгрузили 1000, оплачено 1000, возврат товара 300 и возврат
денег 300) после первой закупки у него на 500 старые 300 «стали» оплатой
поставщику: продажи −300 вместо 0, закупки 200 вместо 500. По
предложению — 0 и 500, и после отмены той закупки назначение не меняется.

**Предлагаемое поле платежа — «Назначение для взаиморасчётов»:**

| Значение | Направление | Сторона |
|---|---|---|
| Оплата от покупателя | только входящий | продажи: долг покупателя уменьшается |
| Возврат покупателю | только исходящий | продажи: долг покупателя растёт |
| Оплата поставщику | только исходящий | закупки: наш долг уменьшается |
| Возврат от поставщика | только входящий | закупки: наш долг растёт |
| Не распределено | любой | ни одна; показывается отдельно |

Ссылка на счёт покупателю означает «оплата от покупателя» (счёт — продажа).
Поле «покупатель / поставщик» в карточке контрагента назначение конкретного
платежа не доказывает и не используется.

## Старые платежи и корректировки

- **Однозначно:** входящий платёж со ссылкой на счёт покупателю — «оплата
  от покупателя».
- **Остальные — «не распределено»**, без угадывания. Диагностика
  показывает их списком по парам с подсказкой («у пары только продажи —
  вероятно, оплата от покупателя»), но назначение ставит человек.
- На копии локальной базы: 5 проведённых платежей — 3 однозначно (по
  счетам), 2 уточнить (входящие 488 и 490 от АО «СЕВТЕЛЕКОМ» без счёта).
- Пока у пары есть нераспределённые деньги или корректировки без стороны:
  они видны отдельной строкой, задолженности по продажам и закупкам
  помечены как предварительные, итог по паре — **справочная разница по
  документам** (её сумма от назначения не зависит). Пример: отгрузили 1000,
  приняли 700, получили 400 без назначения → продажи 1000 и закупки 700
  (предварительно), не распределено 400, разница −100; после уточнения
  «оплата от покупателя» — 600 и 700, окончательно.

## Взаимозачёт и корректировки

- **Существующая корректировка зачёт не выражает.** Покупатель должен
  1000, мы ему как поставщику 700, разница 300. Зачёт на 700 должен дать
  300 и 0, разница по-прежнему 300. Корректировка «мы должны 700» меняет
  разницу: 1000 − 700 − 700 = −400. Зачёт — это две записи по сторонам
  (продажи −700 и закупки −700). **В первом этапе зачёта нет**: обе стороны
  показываются отдельно.
- **Направление корректировки задаёт знак, но не сторону.** «Он должен
  100» может означать недовыставленную продажу (продажи +100) или
  переплату поставщику (закупки −100): задолженности разные (1100/700 или
  1000/600), разница одна (400). Новым корректировкам — поле стороны
  («продажи» / «закупки»); старые — «без стороны»: в стороны не
  распределяются, показываются отдельно и входят только в справочную
  разницу.

## Проверки (модель и сценарии на документах)

| Проверка | Где |
|---|---|
| Первая закупка не переклассифицирует старый возврат денег покупателю; первая продажа — старый возврат денег поставщиком | модель |
| Отмена закупки не меняет назначение платежа | модель |
| Организации не гасят долги друг друга (А: он должен 1000; Б: получено 1000 — отдельно) | модель, сценарий 7 |
| Одинаковая разница 300 — разные задолженности (300/0 и 1000/700) | модель |
| Платежи без назначения видны, итог помечен справочным | модель, сценарии 6, 8, 9 |

## Минимальный план (выполнен 18.10.2026)

1. Поле «Назначение для взаиморасчётов» в платеже (пять значений,
   проверка соответствия направлению; в форме — выбор, для платежа по счёту
   — «оплата от покупателя» автоматически). Поле «сторона» в корректировке
   взаиморасчётов.
2. Миграция: старым платежам — «оплата от покупателя» только при ссылке на
   счёт, остальным — «не распределено»; старым корректировкам — «без
   стороны». Ничего не угадывается.
3. Диагностика нераспределённых платежей и корректировок с подсказками;
   уточнение — вручную в карточке платежа.
4. Отчёт «Взаиморасчёты»: строки по паре «организация + контрагент» —
   продажи, закупки, не распределено, корректировки без стороны, разница
   (справочная, пока есть нераспределённое); итоги «нам должны» / «мы
   должны» отдельно. Карточка контрагента — та же сводка.

Не входит: автоматический взаимозачёт, бухгалтерские проводки, договорной
учёт, закрытие периодов, привязка платежей к конкретным отгрузкам.
