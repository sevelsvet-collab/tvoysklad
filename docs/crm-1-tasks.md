# CRM-1: задачи сотрудникам — задание на реализацию

Дата: 08.11.2026. Подготовлено по исходникам main b5f7688. Статус: проект контракта первой версии, готовый для проверки реализатором. Рабочий сервер не изменять.

10.11.2026: контракт сверен с кодом и реализован в ветке `feature/crm-tasks`; уточнения сверки и принятые решения — в разделе 12, как пользоваться — в разделе 13, проверка и установка — в разделе 14. Общий план — [crm-roadmap.md](crm-roadmap.md).

## 1. Проверенное исходное состояние

- В templates/sales/{invoice,shipment,customer_return}_form.html, templates/purchases/{receipt,supplier_return}_form.html и templates/finance/payment_form.html «Задачи» и «События» представлены отключёнными кнопками. Подтверждённого готового модуля задач при поиске по apps не найдено.
- apps/core/models.py содержит существующего User с display_name и проверкой ролей через группы.
- Роли: Администратор, Менеджер, Кладовщик, Бухгалтер. Суперпользователь проходит has_role независимо от групп.
- apps/core/permissions.py проверяет вход и роли; эту проверку нельзя считать проверкой участия в конкретной задаче.
- Страница пользователей доступна администратору. Новый справочник сотрудников не нужен.
- Разграничение по организациям для CRM нельзя считать уже реализованным: перед кодом проверить фактические ограничения исходных документов. Не заявлять изоляцию организаций без соответствующих проверок.

## 2. Результат первого выпуска

Менеджер или администратор ставит задачу сотруднику. Сотрудник видит её в «Моих задачах», выполняет чек-лист, пишет результат. Постановщик принимает результат либо возвращает на доработку. Задача может быть самостоятельной или связанной с существующим документом. Складские и денежные движения при этом не меняются.

В этот выпуск не входят: заказ покупателя, сделки, канбан продаж, резервы, интеграция сайта, роботы, почта/Telegram, файлы, наблюдатели, соисполнители, подзадачи, учёт рабочего времени и общий корпоративный чат. Заказы добавляются следующим модулем; модель задач не должна требовать их наличия.

## 3. Данные задачи

- Автоматический стабильный номер.
- Заголовок и описание обычным текстом, без пользовательского HTML.
- Постановщик (текущий пользователь, подмену из POST запрещать).
- Один основной исполнитель: активный сотрудник из существующей системы ролей.
- Срок с датой и временем; часовой пояс интерфейса обозначен явно.
- Приоритет: обычный, высокий. Просрочка вычисляется, а не выбирается вручную.
- Статус, флаг «Требуется проверка результата» и текст результата.
- Чек-лист, комментарии, журнал действий.
- Не более одного основного связанного объекта в первой версии: контрагент, счёт покупателю, отгрузка, приёмка, возврат покупателя, возврат поставщику или платёж.
- Даты создания, изменения и завершения, версия записи для защиты от потери параллельных изменений.

Задача может быть без документа. Связь добавляется только с сохранённым объектом, доступным пользователю. Типы объектов ограничены явным списком. Не допускать произвольного обращения к моделям через входные content_type/id. Способ хранения выбирает реализатор после изучения удаления документов; защита ссылочной целостности обязательна.

## 4. Состояния и действия

Новая → В работе → На проверке → Завершена.

- Если проверка не требуется, исполнитель завершает задачу из «В работе» с результатом.
- Если проверка требуется, исполнитель сдаёт результат, постановщик или администратор принимает либо возвращает в работу. Причина возврата обязательна.
- «Ожидание» доступно из новой/в работе с обязательной причиной; возврат из ожидания — в работу. Срок при ожидании автоматически не переносится.
- Отменяет постановщик или администратор с причиной; из любого незавершённого состояния.
- Возобновляет завершённую или отменённую задачу постановщик/администратор с причиной; она переходит в работу. Старое завершение и результат остаются в истории.
- Переназначение исполнителя возвращает незавершённую задачу в «Новую», требует причины, уведомляет прежнего и нового исполнителя. Из «На проверке» сначала вернуть в работу. Завершённую/отменённую сначала возобновить.
- Совпадение постановщика и исполнителя допустимо; для такой задачи проверка результата отключена, чтобы не обещать независимую приёмку.
- Чек-лист редактирует постановщик/администратор до сдачи результата; исполнитель отмечает пункты в новой/в работе/ожидании. Для сдачи все существующие пункты должны быть отмечены; отсутствие пунктов допустимо.
- После завершения доступны просмотр и комментарии, но поля задачи и отметки не редактируются до возобновления.
- Удаления задач нет: отмена сохраняет историю. Комментарии в первой версии не редактируются и не удаляются.

Просрочена: срок прошёл и задача не завершена/не отменена. Задачи на проверке с прошедшим сроком также видны как просроченные, но выделяются отдельно как ожидающие приёмки. Факт сдачи и факт приёмки имеют разные отметки времени.

## 5. Права

| Действие | Администратор | Менеджер | Кладовщик / бухгалтер |
|---|---|---|---|
| Создать поручение другому сотруднику | Да | Да | Нет в первой версии |
| Создать задачу себе | Да | Да | Да |
| Видеть задачи | Все задачи | Только где постановщик или текущий исполнитель | Только где постановщик или текущий исполнитель |
| Менять содержание, срок, исполнителя | Да | Если постановщик | Если постановщик своей задачи |
| Выполнять и сдавать результат | Если исполнитель | Если исполнитель | Если исполнитель |
| Принимать/возвращать/отменять | Да | Если постановщик | Если постановщик |
| Читать историю и комментировать | Да | Если есть доступ к задаче | Если есть доступ к задаче |

Это предложенная политика первого выпуска. Новую роль монтажника или техника не подменять выдачей прав кладовщика; отдельную роль рассмотреть следующим расширением.

Для связанной задачи постановщик и исполнитель должны иметь право просмотра исходного объекта при назначении. Если такого права нет, назначение блокируется с понятным объяснением; автоматически расширять доступ или копировать содержимое документа нельзя.

При потере права на исходный документ доступ участника к связанной задаче временно закрывается полностью, включая поиск, комментарии и уведомления: текст задачи мог содержать сведения документа. Администратор видит проблему и может переназначить задачу. В первой версии смену/удаление связи после создания запретить, чтобы не открыть ранее закрытый текст. Для поручения сотруднику без доступа создаётся отдельная самостоятельная задача с необходимым минимумом данных.

Доступ к документу проверяется по тем же правилам, что и сам документ, а не по наличию ссылки в задаче. Видимость вкладки задач в документе не открывает чужие задачи: счётчик и список учитывают только доступные текущему пользователю.

При отключении исполнителя не удалять историю и не делать автоматическое переназначение. Администратору показывать активные задачи отключённых сотрудников. Пользователей, связанных с задачами, защищать от физического удаления, использовать деактивацию. История прежнего исполнителя остаётся, но его доступ после переназначения прекращается, если он не постановщик.

## 6. Экраны

### Список «Задачи»

Верхнее меню: отдельный пункт «Задачи». Представления: «Мне», «Порученные мной», «На проверке»; «Все задачи» только администратору. Везде можно показать завершённые отдельным фильтром.

Колонки: номер, заголовок, статус, исполнитель, срок, приоритет, связанный объект. Фильтры: статус, срок, просрочка, исполнитель и текст. Фильтры не расширяют права. Пагинация; без массового редактирования в первом выпуске.

### Карточка

Шапка: заголовок, статус, исполнитель и срок. Описание и ссылка на доступный документ. Чек-лист. Доступные действия по статусу. Лента комментариев и системных событий с автором и временем. Форма комментария отдельно от формы изменения задачи, без вложенных HTML-форм.

### Из документа

Активировать «Задачи» для перечисленных сохранённых документов. Кнопка «Поставить задачу» открывает отдельную форму с уже выбранным основанием. Не отправлять основную форму документа и не перепроводить его при создании задачи. У несохранённого документа предложить сначала сохранить документ.

«События» документов пока не активировать: журнал первой версии относится только к задаче, полноценный аудит всех документов — отдельный этап.

### Телефон

Список читается как карточки, действия не требуют горизонтальной прокрутки. Выполнение задачи и отправка комментария доступны без открытия широкой таблицы исходного документа.

## 7. Уведомления и история

Внутренний список уведомлений: назначили/переназначили, изменили срок, сдали результат, приняли/вернули, отменили, добавили комментарий. Автор действия не уведомляет сам себя. Постановщик и исполнитель получают только релевантные события и не более одного уведомления на событие.

Для уведомления хранить ссылку и идентификатор события; отображаемые подробности проверять по текущему доступу. Нельзя сохранять закрытый заголовок в публичном счётчике или списке после потери прав.

Периодические напоминания, push и внешний обмен отложены. Просрочка отображается при чтении списка. Redis/Celery для этого выпуска не требуются.

Журнал изменений содержит автора, время, действие и старое/новое значение для срока, исполнителя, статуса, проверки результата, заголовка/описания и чек-листа. Комментарии фиксируются отдельно. Историю нельзя редактировать обычными формами или Django admin. Изменение задачи, событие и запись уведомлений атомарны.

## 8. Целостность и параллельная работа

- Проверки прав и переходов повторяются на сервере для каждого изменения. CSRF обязателен, GET ничего не меняет.
- Повторная отправка создания не создаёт вторую задачу; повторное принятие не создаёт второй результат и уведомления. Переиспользовать существующий механизм токенов, если подходит после проверки.
- Две открытые формы: позднее сохранение устаревшей версии выдаёт конфликт и предлагает обновить страницу, а не затирает новую запись.
- Переходы состояний выполняются в транзакциях с проверкой текущего состояния; тестировать на PostgreSQL.
- Связанный документ/контрагент нельзя физически удалить при наличии задачи: понятный отказ, без частичного удаления. Отмена задачи связь не уничтожает. Проверить обычное, массовое удаление и административный путь.
- Проведение и отмена проведения исходного документа не меняют задачу автоматически. CRM никогда не пишет StockMovement, остатки, Payment или суммы взаиморасчётов.
- Индексы и пагинация для списков задач, истории и уведомлений; избежать запроса по каждой строке списка.

## 9. Приёмочные сценарии

1. Менеджер создаёт поручение активному исполнителю; задача появляется в «Мне», постановщик видит её в «Порученных мной».
2. Исполнитель начинает, отмечает чек-лист, сдаёт результат; постановщик возвращает с причиной, затем принимает. Журнал содержит весь цикл.
3. Задача без проверки завершается исполнителем; самостоятельно включить/отключить чужую проверку он не может.
4. Ожидание не скрывает просрочку; отменённая задача не показывается как активная.
5. Неучастник не видит задачу, комментарии, уведомления и счётчик ни через интерфейс, ни через прямые GET/POST.
6. Подмена постановщика, исполнителя, связанного типа/id и статуса отклоняется без частичных изменений.
7. При деактивации сотрудника история остаётся, задачи видны администратору; при переназначении новый исполнитель получает доступ, старый теряет его.
8. Утрата доступа к связанному документу закрывает задачу и её текст во всех представлениях.
9. Удаление основания с задачей блокируется и не меняет учёт. Проверить также массовое удаление.
10. Создание, комментарии и завершение задачи не меняют состояние/версию учётного документа, складские движения, деньги и долги.
11. Повтор отправки не создаёт дублей. Конкурентное редактирование и двойная приёмка дают определённый результат на PostgreSQL.
12. Браузерный сценарий от документа до принятия задачи под разными пользователями. Чек-лист и комментарий работают на узком экране.
13. HTML/скрипт в названии и комментарии отображается текстом. Не отключать существующие проверки загрузок и безопасности.
14. Обновление существующей базы добавляет пустые таблицы задач без фиктивных задач, новых пользователей и изменения прежних документов.

## 10. Порядок реализации и поставки

1. Прочитать правила репозитория и подтвердить актуальный main. Не работать параллельно с другой сессией в одной папке.
2. Коротко сверить этот контракт с кодом: особенно права чтения документов, удаление, пользователи, токены повторной отправки. Сообщить реальные противоречия до изменения модели.
3. Новая ветка feature/crm-tasks. Изолированная тестовая база, не использовать рабочую .env.
4. Модель и серверные операции, тесты прав/состояний/конкуренции; затем интерфейс и браузерные сценарии. Не подключать сайт и не строить заказы в этой ветке.
5. Проверить миграции на копии схемы/данных; выполнить связанные тесты и полный прогон, поскольку меняются общая навигация и связи документов. Явно перечислить пропуски и среду.
6. Отчёт: файлы, миграции, проверенное дерево, результаты, ограничения, инструкция проверки и отката. При откате образа учитывать новые задачи: не удалять их таблицы без отдельного решения.
7. Публикация и установка отдельным этапом после проверки; этот документ не разрешает обновлять рабочий сервер, отправлять сообщения сотрудникам или подключать внешние каналы.

## 11. Решения, которые можно уточнить по первому использованию

Первая политика допускает постановку чужих задач только менеджером и администратором. Отдельную роль руководителя, наблюдателей, технических сотрудников и более гибкую видимость добавлять после подтверждения потребности. Два реальных процесса владельца нужны прежде всего для будущих заказов и шаблонов; базовые поручения не зависят от выбора конкретной отрасли.

## 12. Уточнения по результатам сверки с кодом (10.11.2026)

Сверено с main b5f7688. Существенных противоречий с контрактом не найдено. Пункты 1–3 подтверждены владельцем 10.11.2026; остальные — решения реализатора в рамках контракта, их можно пересмотреть по первому использованию.

1. **Право на связанный объект — право открыть его карточку.** Используются те же роли (`allowed_roles`), что проверяет представление карточки документа или контрагента; они читаются из самого представления ([apps/tasks/links.py](../apps/tasks/links.py)). Списки документов и печатные формы основанием для доступа к задаче не служат. Сейчас они проверяют только вход в программу — это зафиксировано отдельным дефектом и в ветке CRM-1 не исправлялось. Сведений задач в них нет. Проверка права выполняется при назначении и при каждом чтении задачи, комментариев, истории, списков, поиска, счётчиков и уведомлений.

   | Связь | Роли карточки |
   |---|---|
   | Контрагент | администратор, менеджер, бухгалтер |
   | Счёт покупателю | администратор, менеджер |
   | Отгрузка, возврат покупателя | администратор, менеджер, кладовщик |
   | Приёмка, возврат поставщику | администратор, менеджер, кладовщик |
   | Платёж | администратор, менеджер, бухгалтер |

2. **Разграничения по организациям в программе нет** — ни для документов, ни для задач. Права зависят только от ролей. CRM-1 изоляцию организаций не обеспечивает и не заявляет.
3. **Удаление.** Связь хранится отдельным внешним ключом на каждый тип объекта с запретом удаления (`on_delete=PROTECT`) и ограничением базы «не более одной связи». До CRM-1 одиночное удаление документов не обрабатывало такой отказ: после появления связей из задач оно давало ошибку 500. Это воспроизведено тестом, затем добавлен понятный отказ без частичных изменений: [apps/core/protection.py](../apps/core/protection.py) и обработчики удаления документов. Массовое удаление через общий механизм ([apps/core/bulk.py](../apps/core/bulk.py)) отказ уже показывало — уточнён его текст. Административная панель отказывает средствами Django. Если задачу ставят к счёту в тот же момент, когда счёт удаляют, удаление отклоняет база при записи — с сообщением «обновите страницу»; у складских документов и платежей удаление и постановка задачи ждут друг друга по блокировке строки.
4. **Сотрудник** — активный пользователь с одной из ролей (или суперпользователь). Пользователь без роли задач не видит и не может быть исполнителем.
5. **Номер задачи** — её идентификатор: постоянный, без серии по организации и году.
6. **Срок** необязателен: задача без срока не бывает просроченной. Время — по часовому поясу программы (московское), это подписано в форме и карточке.
7. **Ожидание** ставит и снимает исполнитель.
8. **Возврат на доработку** снимает отметку сдачи; прежний результат подставляется в форму для дополнения, все версии результата остаются в журнале. **Возобновление** очищает результат и отметки завершения, прежний результат сохраняется в журнале.
9. **Уведомления.** Сверх перечня раздела 7 уведомляют также о завершении задачи исполнителем без проверки (постановщику) и о возобновлении (исполнителю). Прежний исполнитель после смены исполнителя видит уведомление «задача передана другому исполнителю» без заголовка и ссылки. Если прежнему исполнителю недоступен связанный документ, это уведомление тоже скрыто. Отметка «прочитано» ставится только POST-запросом: открытие страниц ничего не меняет.
10. **«На проверке»** у администратора показывает все задачи на проверке, у остальных — те, где они постановщик.
11. Пункт чек-листа при удалении помечается удалённым, а не стирается, — журнал ссылается на его текст.
12. Вкладка «Задачи» включена и в карточке контрагента; «События» документов остаются выключенными.

## 13. Как пользоваться

- **Меню «Задачи»**: «Мне», «Порученные мной», «На проверке», «Все задачи» (только администратор), «Уведомления». Колокольчик в верхней панели показывает число непрочитанных уведомлений.
- **Поставить задачу**: кнопка «Задача» в списке или вкладка «Задачи» → «Поставить задачу» в карточке сохранённого документа (связь подставится сама). Кладовщик и бухгалтер ставят задачи только себе.
- **Исполнитель**: «Взять в работу» → отметить пункты чек-листа → «Сдать результат» (если постановщик включил проверку) или «Завершить». При задержке — «Перевести в ожидание» с причиной.
- **Постановщик**: «Принять результат» или «Вернуть на доработку» с причиной; «Изменить» — заголовок, описание, срок, приоритет, проверка, чек-лист; «Сменить исполнителя» с причиной; «Отменить» и «Возобновить» с причиной.
- **Администратор**: «Все задачи», фильтр «Проблемы» — активные задачи отключённых сотрудников и задачи, участники которых потеряли доступ к связанному документу.
- На телефоне список показывается карточками; чек-лист, комментарий и действия доступны без широкой таблицы документа.

Код: [apps/tasks/](../apps/tasks/) — модели, права ([access.py](../apps/tasks/access.py)), операции ([services.py](../apps/tasks/services.py)), экраны; шаблоны — `templates/tasks/`.

## 14. Установка и откат

Миграция одна: `tasks.0001_initial` — пять новых пустых таблиц задач, без изменения прежних таблиц и без создания пользователей. На копиях данных проверено: прежние таблицы совпадают до и после, кроме служебных — права, типы содержимого и журнал миграций.

Установка — обычным порядком выпуска ([release-readiness.md](release-readiness.md)): свежая резервная копия базы → сборка образа → `migrate` → `check` → проверка страниц → запуск. Новых переменных окружения, фоновых процессов, Redis и Celery нет.

Откат образа (вернуть прежний код) таблицы задач **не удаляет** — так созданные задачи сохраняются:
- прежний код таблицы задач не использует; `migrate` в нём ничего не применяет, страницы работают;
- база по-прежнему защищает задачи. Если прежний код попытается удалить документ, контрагента или пользователя, на которых ссылается задача, база откажет (в прежнем коде — страница ошибки) и ничего не удалит;
- при повторной установке новой версии задачи снова видны.

`migrate tasks zero` удаляет таблицы задач вместе со всеми задачами — только по отдельному решению и после резервной копии.
